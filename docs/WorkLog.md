### OQ-031 수정 — 방 1(무전투)의 빈 텔레메트리가 방 3 분석을 희석하던 문제

- 상태: DONE
- 관련 계획: 없음(버그 수정, 별도 DEC 없이 처리)
- 관련 질문: OQ-031 (RESOLVED)

#### 작업

- `RunState.completeRoom()`이 무조건 `this.previousTelemetry = this.currentTelemetry`로
  넘기던 것을, 넘기려는 텔레메트리가 "신호"(근접+원거리 적중 또는 대시 중 하나라도
  0보다 큼)가 있을 때만 넘기도록 바꿨다. 신호가 없으면(방 1 튜토리얼처럼) `null`로
  둔다 — `analyze()`가 `previous=null`을 받으면 현재 방 100% 가중치로 처리하므로,
  OQ-011이 방 1 자신에 대해 이미 정한 규칙("이전 방 없으면 현재 방 100%")을 방 2
  입장에서도 동일하게 적용하는 셈이다.

#### 오류 및 원인

- 증상: 방 1이 무전투가 되면서 항상 빈 텔레메트리를 만들어 내고, 이게 방 2 클리어
  시점에 `previousTelemetry`로 넘어가 방 3 선택용 분석(`analyze(room2, room1Empty)`)의
  35% 가중치 자리를 차지했다.
- 재계산해보니 영향 범위는 처음 생각보다 좁았다 — `classify()`의 근거리/원거리 비율은
  분자·분모가 둘 다 0.65배로 스케일되어 실제로는 **비율 자체가 변하지 않는다**(수학적으로
  상쇄됨). 실제로 희석되는 건 **대시 횟수(`dashCount`)뿐**이다 — 방 1이 대시 0을
  "이전 방"으로 넘기면 방 2의 실제 대시 횟수가 0.65배로 깎여 MOBILE 판정 임계값(8)에
  도달하기 더 어려워지고 신뢰도도 낮아진다. 즉 원래 우려("근거리/원거리 판정이
  둔감해진다")는 부정확했고, 정확히는 "MOBILE 판정만 둔감해진다"였다.
- 원인: `completeRoom()`이 방의 성격(전투 여부)을 구분하지 않고 기계적으로 윈도우를
  한 칸씩 미는 구조였다.

#### 검증

- `npm run typecheck`, `npm run lint`, `npm run build` 통과.
- `window.runState` 훅으로 실제 전투 없이 상태만 조작해 결정적으로 확인했다:
  방1(빈 텔레메트리) → 방2(대시 10회 등 실신호) 클리어 후 `previousTelemetry`가
  **정확히 `null`**임을 확인(수정 전이라면 방1의 빈 객체였을 자리). 이어서 방2(신호
  있음) → 방3 클리어를 시뮬레이션해 `previousTelemetry`가 방2의 실제 텔레메트리
  (`dashCount: 10` 등)를 그대로 담고 있음도 확인 — 신호가 있는 정상 케이스의 65/35
  가중은 회귀 없이 그대로 동작한다.
- 실제 콤보/전투 흐름을 헤드리스로 재현하지는 않았다(위 항목대로 자동화가 새 전투
  난이도에서 계속 사망). 상태 조작 검증이 `classify`/`analyze`의 순수 함수 특성상
  실전투 재현과 동일한 결론을 준다고 판단해 이걸로 충분하다고 봤다.

#### 남은 작업

### 화염·맹독 속성탄 킬 시 크래시 수정

- 상태: DONE
- 관련 계획: 없음(버그 수정)
- 관련 AI 로그: AI-019

#### 오류 및 원인

- 사용자 보고: 방 2에서 원거리 모드로 전환해 사격하던 중, 맹독탄(`RANGED_POISON_ROUND`)
  강화를 획득한 직후 다음 발을 쏘려는 순간 `Cannot read properties of null (reading 'x')`로
  크래시. 브라우저 콘솔의 프로덕션 번들 스택만으로는 위치를 특정할 수 없어, 사용자에게

  물어 좁혔다.
- 원인: `CombatScene.applyElement`(FIRE·POISON)와 `BossScene.applyElement`(동일 구조)의
  지연 틱 데미지 콜백이
  ```
  if (enemy.isDefeated || !enemy.sprite) return;
  enemy.takeDamage(tickDamage);
  damageNumber(this, enemy.sprite.x, enemy.sprite.y - 30, tickDamage);
  ```
  순서였다. `takeDamage()`가 이 틱으로 적을 죽이면 `BaseEnemy.defeat() → playDeathEffect()`
  가 그 안에서 즉시 `this.sprite = null`을 실행하는데(`BaseEnemy.ts:258`, `Boss.ts`도 동일),
  바로 다음 줄이 이미 null이 된 `sprite.x`를 읽어 크래시로 이어졌다. `isDefeated`/`sprite`
  가드는 콜백 진입 시점만 확인해, 콜백 실행 중 상태가 바뀌는 경우를 놓치고 있었다.
- 화염 속성도 같은 구조라 동일 조건(지연 틱이 마무리타가 되는 순간)에서 언제든
  재현 가능했다 — 사용자가 맹독으로 먼저 밟은 것일 뿐 속성 종류와는 무관한 버그다.

#### 수정

- 4곳(`CombatScene.ts`의 FIRE·POISON, `BossScene.ts`의 FIRE·POISON) 모두 `takeDamage()`
  호출 **전에** `sprite.x`/`sprite.y`를 지역 변수로 먼저 캡처하도록 순서를 바꿨다.
  `BaseEnemy.defeat()`가 파괴 전에 좌표를 먼저 붙잡아 두는 것과 같은 패턴이다.

  스텁으로 바꿔 타이밍에 의존하지 않고 같은 코드를 그대로 태웠다.
