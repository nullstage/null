# AI 사용 기록 — 2026-08-08

## AI-002 — 적 패턴·강화 카드·Director 방 분류 구현 상태 조사

### 목적

팀원이 진행해 둔 전투 구현을 이어받기 전에, `docs/Plan.md`에 DONE으로 표시된
DirectorPolicy·적 3종·강화 시스템이 실제 코드에서 어디까지 동작하는지 확인하기 위해서다.
문서 표기만으로는 미결정 정책(OpenQuestions)과 실제 구현 여부가 뒤섞여 있어 구분이 필요했다.

### 사용 도구

Claude Code (Sonnet 5), 조사 전용 서브에이전트(Explore) 1개

### 대표 프롬프트

```text
팀원이 작업을 좀 해놨는데, 적 패턴 제작이랑 방 깼을 때 나오는 강화 카드를 더 구체화하고
싶다. 방을 깨면 근거리/원거리 패턴을 분석해서 다음 방을 바꾸는 것도 얼마나 구현돼있는지
확인해야 한다.
```

### AI 제안 요약

- 적 3종(ChaserEnemy·RangedEnemy·MobilityCounterEnemy)은 스탯이 아니라 상태머신 기반
  행동으로 차별화되어 있으며 완전히 구현됨을 파일:라인 근거와 함께 확인.
- 강화 8종이 전부 정의되고 `Player.ts`에서 실제 스탯에 적용됨을 확인. 다만 지급 횟수가
  2회로 고정돼 있고 OQ-016(3회 권장)이 코드에 반영되지 않았음을 지적.
- DirectorPolicy의 스타일 분류가 방 3(카운터 방)과 보스 패턴 가중치에는 실제로
  연결되지만, 방 2는 방 1 분석을 반영하지 않는 고정 프리셋임(OQ-010 미반영)을 지적.

### 최종 반영

조사 결과를 바탕으로 사용자에게 OQ-010(방2 반영 여부)과 OQ-016(강화 지급 횟수)을
확정하도록 질문했다. 결정된 내용(약한 카운터 적용 / 3회 지급)을 `DecisionLog.md`
DEC-013·DEC-014로 기록하고(2026-08-09 main 병합 시 팀원 쪽과 번호가 겹쳐
DEC-015·DEC-016으로 재번호했다), DEC-015(강화 3회)는 바로 구현·검증까지 마쳤다.
DEC-016(방2 반영)은 구체적 반영 방식(스폰 순서 조정 / 적 1종 교체 / 축소판 카운터방)을
다시 질문해 결정을 받은 뒤 구현했다(AI-003).

### 사람의 수정 및 판단

- 방2 반영 방식은 AI가 임의로 확정하지 않았다. 방2가 방3 분석에서 "이전 방" 자리를
  차지해 35% 가중치를 그대로 받는 구조라(MVP_PLAN §4), 반영 방식에 따라 "방1 분석 →
  방2 구성 → 방3 분석"이 서로 되먹임하는 위험이 있다고 판단해 별도 결정 사항으로 분리했다.
- 강화 3회 지급은 결정되자마자 구현까지 진행했지만, 완료 보고 전에 반드시 실제
  브라우저 흐름을 관통시켜 검증하라는 프로젝트 규칙에 따라 빌드 성공만으로 끝내지 않고
  Playwright 헤드리스로 방1→방2→방3→강화(3회)→보스 진입까지 실제 클릭으로 재현했다.

## AI-003 — 방 2 소프트 카운터 구체안 구현

### 목적

DEC-016(당시 번호는 DEC-014, main 병합 후 재번호)에서 방향("방 2도 방 1 분석을
약하게 반영")만 정해졌던 것을, 실제로 어떤
방식으로 반영할지 사용자에게 구체적 대안을 제시해 고르게 하고 구현하기 위해서다.

### 사용 도구

Claude Code (Sonnet 5)

### 대표 프롬프트

AskUserQuestion으로 제시한 세 대안(직접 대화 프롬프트 없음):

```text
1. 스폰 순서·타이밍만 조정 (적 종류·수 그대로)
2. 적 1종만 성향에 맞게 교체
3. 축소판 카운터 방 (counter_* 재사용, 2기로 축소)
```

각 대안에 방 1이 RANGED로 감지됐을 때 방 2 스폰 구성이 구체적으로 어떻게 되는지
미리보기로 붙여, "약하게 반영한다"는 말이 실제로 어떤 방 모양이 되는지 보고 고르게 했다.

### AI 제안 요약

세 대안 모두 구현 가능하다고 판단했지만, 축소판(3안)이 방 3 텔레메트리 되먹임
위험이 가장 크다는 점을 미리 경고했다 — 방 2를 특정 스타일로 완전히 밀어붙이면
방 1의 분석 결과가 방 2 자신의 데이터를 통해 방 3 분석에 다시 강화되는 자기실현적
구조가 될 수 있어서다.

### 최종 반영

사용자가 3안(축소판)을 선택했다. 방 3용 카운터 조합에서 다수 그룹(2기)만 남기고
소수 그룹(1기)은 빼는 방식으로 `room_2_soft_ranged`·`room_2_soft_melee`·
`room_2_soft_mobile` 3개 프리셋을 추가하고, `CombatScene.resolveRoomId`가 방 1
단독 분류 결과로 방 2 프리셋을 고르도록 구현했다. `MVP_PLAN.md` §5에 규칙을
문서화하고 `DecisionLog.md` DEC-016(당시 DEC-014)을 `ACCEPTED`로 갱신했다.

### 사람의 수정 및 판단

- 위험을 알고도 축소판을 선택한 것은 사용자 판단이다. AI는 대안과 위험만 제시하고
  결정은 임의로 하지 않았다(CLAUDE.md "핵심 전투 방식/게임 루프 변경은 질문" 원칙).
- 완료 보고 전 실제 브라우저 검증 규칙에 따라, 빌드·타입체크만으로 끝내지 않고
  Playwright로 실제 원거리 전투(모드 전환·사격)를 재현해 방 1이 RANGED로 분류되고
  방 2가 실제로 축소판(2기)으로 바뀌는 것을 스크린샷까지 남겨 확인했다.
- 헤드리스 자동화 중 `page.keyboard.press()`가 Phaser의 `JustDown` 판정을 놓쳐
  입력이 무시되는 문제를 만났다 — 제품 버그가 아니라 테스트 방식 문제임을 먼저
  확인(이동 키는 정상 동작)한 뒤 `down`→대기→`up` 방식으로 바꿔 해결했다.

  `src/game/scenes/CombatScene.ts`
- `docs/OpenQuestions.md`, `docs/DecisionLog.md`, `docs/Plan.md`, `docs/WorkLog.md`

## AI-007 — 패링 시스템 설계 및 구현

### 목적

전투에 반격 수단이 없어 일방적으로 받기만 하는 느낌이라, S키로 발동하는 패링과 퍼펙트 판정 시
피해 반사를 추가하기 위해서다.

### 사용 도구

Claude Code (Sonnet 5)

### 대표 프롬프트

```text
패링 추가 (s키로 작동, 퍼펙트 패링시 딜 반사)
```

이후 범위 확인을 위한 AskUserQuestion에 다음과 같이 답함:

```text
지금 바로 넣는다 (권장)
```

### AI 제안 요약

- 판정창을 2단계로 제안: 퍼펙트(무피해+반사) / 늦은 블록(경감 피해, 후속타 대응 유지).
- 반격 대상 참조는 DEC-011 계약(엔티티가 서로 직접 참조하지 않음)에 맞춰, 공격체에
  `setData("source", ...)`를 태깅하고 씬 충돌 핸들러가 반사를 라우팅하는 방식을 제안.

### 최종 반영

`Player.ts`에 퍼펙트 160ms / 블록 340ms(25% 경감) / 쿨타임 900ms로 구현. `takeDamage()`가
`{ parried, perfect }`를 반환하도록 바꾸고, `CombatScene.ts`·`BossScene.ts`의 충돌 핸들러에서
퍼펙트일 때만 공격 주체에 반사 데미지를 적용했다. 모든 적 공격체(`ChaserEnemy`/`RangedEnemy`/
`MobilityCounterEnemy`/`Boss`)에 `source` 태깅을 추가했다.

### 사람의 수정 및 판단

- 이후 피드백으로 퍼펙트 성공 이펙트를 "보호막이 팡 하고 터지는" 느낌으로, 사운드는 발동
  시점이 아니라 성공 시점에 재생하도록 재작업(`perfectParryBurst`, `parryGuard`를 삼각함수
  기반 궤도 이펙트로 교체).

### 관련 파일

`src/game/entities/Player.ts`, `src/game/scenes/CombatScene.ts`, `src/game/scenes/BossScene.ts`,
`src/game/entities/enemies/*.ts`, `src/game/entities/Boss.ts`, `src/game/systems/CombatVfx.ts`,
`src/game/config/inputConfig.ts`

## AI-008 — 아티팩트 시스템(스탯트리 + 속성) 설계 및 구현

### 목적

강화(강화 선택)가 8종뿐이라 밸런스가 단조롭고, 공격/유틸/체력 계열로 나뉘는 더 깊은 빌드
다양성과 화염/냉기 같은 속성 부가 효과를 추가하기 위해서다.

### 사용 도구

Claude Code (Sonnet 5)

### 대표 프롬프트

```text
아티팩트 추가 … ( 속성추가 ?? // 나누기 공격중심..유틸중심..체력중심
공격에는 총알크기, 데미지, 속성 / 검 크기, 데미지, 속성 혹은 특수기술(검기같은거)
체력에는 체력재생 (크지 않은) 기본체력, 내구력
유틸에는 대쉬 쿨타임, 연속대쉬 횟수, 대쉬간 무적)
```

이후 진행 순서 확인 AskUserQuestion에 다음과 같이 답함:

```text
아티팩트 먼저 → NPC 강화상 → NPC 이벤트 (권장)
```

### AI 제안 요약

- 속성을 정식 상성/저항 체계로 만들지 말고, 화염=시간차 틱 데미지 / 냉기=이동속도 저하
  두 가지 얕은 효과로 한정할 것을 제안(구현 비용과 밸런스 리스크를 줄이기 위해).
- `UpgradeSystem`을 그대로 두고 `UpgradeId`·`UpgradeCategory`·`UpgradeElement`만 확장하는
  쪽이 별도 ArtifactSystem을 새로 만드는 것보다 낫다고 판단(기존 `rollUpgradeChoices()`가
  카테고리에 무관하게 동작해 변경 없이 재사용 가능).
- 검기(특수기술)는 마무리 타격에서만 발사되는 별도 투사체로 구현(멜리 사거리 자체를
  늘리는 것과 분리).

### 최종 반영

`UpgradeId` 10종 추가(검 크기·화염날·검기 / 총알 크기·냉기탄 / 대시 쿨타임·무적 보너스 /
체력 최대치·재생·경감), `UpgradeCategory`에 `HEALTH` 추가. `applyElement()`를
`CombatScene.ts`·`BossScene.ts` 양쪽에 만들어 화염 틱뎀·냉기 슬로우를 배선했고,
`RunState`가 `HEALTH_MAX_UP`/`HEALTH_REGEN`을 각각 강화 선택 시점·방 클리어 시점에 적용하게
했다.

### 사람의 수정 및 판단

- 체력 강화가 `Player.maxHp`에는 반영되지만 방 전환 시 `RunState.maxHp`와 동기화되는
  코드가 없다는 것을 직접 확인하고, `CombatScene`/`BossScene` 방 진입부에
  `player.maxHp = runState.maxHp` 동기화를 추가로 넣었다(AI 초기 구현에는 없던 부분).
- `TUNING` 상수가 `Player.ts` 안에 비공개로 있어 씬에서 접근할 수 없던 문제를, 새 파일을
  만드는 대신 `export` 하나만 붙여 해결(불필요한 추상화 회피).

`src/game/entities/enemies/BaseEnemy.ts`, `src/game/entities/Boss.ts`,
`src/game/scenes/CombatScene.ts`, `src/game/scenes/BossScene.ts`, `src/game/systems/RunState.ts`

## AI-009 — 야간 일괄 작업: 탄창·속성탄·조각 경제·NPC 이벤트·절차 지형·연출 강화

### 목적
사용자가 자리를 비우는 동안 남은 태스크(#3~#5 대형 시스템 + 전투 개선 6건)를 시각적 완성도 우선으로 일괄 구현.

### 사용 도구
Claude Code (Sonnet 5)

### 대표 프롬프트
> "총알 길이 제한 좀 걸어두고 .. 총 탄창수 제한도 하자 6발 쏘면 재장전하게 ... 클리어 보상같은 경우에 총알 탄창수 증가랑 총알에 속성 뭍히는거 독 불 등등 이런거 넣고 .. ? 그리고 검기는 내 3타 모션같은게 잔상으로 나가야될거같은데 지금처럼 빔이나 총 쏘는 느낌은 좀 안맞는듯"
> "패링은 지금 호 그려지는거 있는데 그것보다는 약간 내 주변에 지금 뭐 돌아다니는데 그거 시각적으로 더 업그레이드 해주고 ... 패링 성공시 약간 쾌감 주게 카메라 무빙이나 뭐 더 추가하는게 좋을듯 ? 그리고 지금 즉거나 죽일때 산화하는거 좋은데 . 너무 빨라서 잘 안보여... 그리고 좀 뒷배경에 핏빛 비 ? 그런거 좀 내리게 하면 좋을거같고 ."
> "나 자고올테니까 남은 태스크 다 완성해놔봐. 일단 최대한 시각적으로 이쁘게 만드는게 최우선이야."

### AI 제안 요약
- 탄창·사거리는 기존 `cullProjectiles`/`beamLine` 구조를 재사용해 최소 배선으로.
- 그림자 조각은 물리 픽업 대신 "흡수 연출 + 즉시 적립"으로 단순화, 상인은 전용 스프라이트 없이 플레이어 시트를 어둠 실루엣으로 재활용.
- 적대 NPC의 매복 추격자는 RoomController 카운트와 분리해 방 클리어 로직 오염 방지.
- 절차 지형은 벽 미로 대신 도달 보장 규칙(다리 강제·점프 거리 제한)의 3층 발판 수직 미로로 축소(OQ-030 등록).

### 최종 반영

## AI-015 — 총(원거리) 타격감 강화와 접지 버그 근본 수정

### 목적
3연사가 "같은 총알 세 번"으로 읽히는 문제 — 발마다 이펙트·피치·반동을 차등하고, 3타 마무리 펀치가 접지 중 충돌 박스를 흔들어 바닥에 파묻히던 버그의 근본 원인 수정.

### 사용 도구
Claude Code

### 대표 프롬프트 (요지 재구성 — 원문 유실)
> 총 쏘는 맛이 밋밋하다. 연사마다 다르게 보이고 들리게 해 달라. 그리고 마무리 사격 때 캐릭터가 땅에 파묻히는 것 같다.

### AI 제안 요약
- 단계별 power(0.75/1.15/2.1)로 총구 섬광·조준선·흔들림·피치를 함께 차등.
- 파묻힘의 원인은 Arcade Body가 scaleY로 충돌 박스를 매 프레임 재계산하는 것 — 접지 중엔 세로 스쿼시를 걸지 않는 것이 근본 수정(착지·대시 버그와 동일 원인).

### 최종 반영
`Player.ts`(RANGED_POWER/DETUNE_BY_STEP, punch의 접지 분기), `CombatVfx.ts`(muzzleFlash·beamLine power 인자). WorkLog "총(원거리) 타격감 강화", "체력바 UI 교체…대시 접지 버그 수정" 참조.

### 사람의 수정 및 판단
- 반동으로 밀리는 체감이 안 온다는 지적 → lungeUntilMs 재사용(이동 입력이 속도를 덮지 않는 창)으로 해결.

### 목적
보유 아티팩트·체력을 확인하는 E키 상태창 신설, "선으로 보이는" 검기 궤적의 1차 광채 스타일 교체, 아티팩트 즉시 부여 테스트 수단 마련.

### 사용 도구
Claude Code (Sonnet 5)

### 대표 프롬프트
> "그리고 검기 날리고 하는 그런 이펙트들 있잖아. 전부 다 선으로 처리하는 경향이 있는데 스킬이펙트처럼 다 화려하게. 지금 검 모션처럼 ?"

- `window.runState` 노출(dev 전용)로 `runState.addUpgrade("ID")` 즉시 테스트.
