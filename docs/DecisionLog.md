## DEC-005 — 기술 스택과 배포 형태

- 날짜: 2026-08-06
- 상태: ACCEPTED
- 관련 질문: OQ-001, OQ-002

### 결정

다음 스택으로 확정한다.

```text
Next.js (App Router) — 셸과 UI 레이어
Phaser 3 — 게임 런타임
GSAP — UI 연출
Emotion — UI 스타일
TypeScript — 전 영역
```

배포는 Next.js 정적 내보내기(`output: "export"`)로 생성한 정적 파일을 GitHub Pages에 올린다.
저장소는 `nullstage/null`을 사용하고 `basePath`는 `/null`로 설정한다.

### 이유

- 팀원이 사용할 스택이 Phaser·Next.js·GSAP·Emotion으로 정해져 있다.
- 정적 내보내기를 쓰면 서버 없이 GitHub Pages에 그대로 올릴 수 있어 DEC-002와 충돌하지 않는다.
- Phaser 메이저 버전은 3으로 고정한다. `MVP_PLAN.md`와 `CLAUDE.md`가 Phaser 3을 전제로 작성되어 있고, 팀원이 참고할 전투·보스 구현 패턴 자료도 3 기준이 압도적으로 많다.

### 대안

- Vite + Phaser 단독: 더 가볍지만 팀원 스택과 어긋나고 Emotion·GSAP UI 레이어를 살리기 어렵다.
- Next.js 서버 렌더링 사용: GitHub Pages가 정적 호스팅이라 불가능하다.
- Phaser 4: 최신이지만 자료가 적고 MVP_PLAN 전제와 어긋난다. 필요하면 별도 결정으로 올린다.

### 영향

- Phaser는 `window`에 의존하므로 정적 프리렌더 중 실행되면 안 된다. 캔버스 컴포넌트는 `ssr: false` 동적 임포트로만 마운트한다.
- 정적 경로 문제 때문에 에셋 경로는 `basePath`를 반영해야 한다.
- `MVP_PLAN.md` §11 파일 구조를 Next.js 구조에 맞게 갱신한다.

## DEC-006 — UI를 React DOM 오버레이로 분리

- 날짜: 2026-08-06
- 상태: ACCEPTED
- 관련 질문: OQ-001

### 결정

분석 팝업, 강화 선택, 결과 리포트, 디버그 패널은 Phaser 내부가 아니라 캔버스 위에 얹는 React 컴포넌트로 구현한다.
Phaser와 React는 단일 이벤트 버스로만 통신하고 서로의 객체를 직접 참조하지 않는다.

```text
Phaser  --emit-->  EventBus  --subscribe-->  React UI
React   --emit-->  EventBus  --subscribe-->  Phaser
```

### 이유

- Emotion과 GSAP을 스택에 넣은 목적이 UI 스타일과 연출이므로 UI가 DOM에 있어야 의미가 있다.
- 팀원은 Phaser 씬과 전투에 집중하고, 시스템 담당은 React UI에 집중할 수 있어 파일 충돌이 줄어든다.
- 텍스트 레이아웃, 반응형, 접근성 처리가 Phaser Text보다 쉽다.

### 대안

- Phaser 내부 UI: MVP_PLAN 원안이지만 Emotion·GSAP이 사실상 사용되지 않는다.
- 혼합: 전투 HUD만 Phaser 내부. 유효한 절충안이라 전투 HUD는 이후 필요 시 Phaser로 옮길 수 있다.

### 영향

- `MVP_PLAN.md` §11의 `src/game/ui/*.ts`는 `src/components/ui/*.tsx`로 대체된다.
- 게임 로직은 React 상태에 의존하지 않아야 한다. UI가 없어도 런은 성립해야 한다.

## DEC-007 — 작업 책임 분리

- 날짜: 2026-08-06
- 상태: ACCEPTED

### 결정

| 영역 | 담당 | 범위 |
|---|---|---|
| 전투 | 팀원 | 플레이어 조작·공격·피격, 적 3종 동작, 보스 상태와 패턴 실행, 타격 피드백 |
| 시스템 | 본인 | 게임 상태, 텔레메트리, Director 정책, 강화, React UI, 이벤트 버스, 배포 |

현재 단계에서는 시스템 영역만 동작하도록 구현하고, 전투 영역은 타입과 호출 시점이 확정된 빈 스텁으로 남긴다.

### 이유

전투 감각은 직접 만드는 사람이 잡아야 하고, 미리 구현해두면 팀원이 버리는 코드가 된다.
반대로 계약과 호출 시점이 없으면 나중에 통합할 때 서로의 파일을 고쳐야 한다.

### 영향

- 스텁 파일에는 구현 대신 `// 팀원 담당` 주석과 시그니처만 둔다.
- 텔레메트리 기록 호출 지점은 시스템 담당이 미리 심어두고, 팀원은 그 자리를 지운다.
- 공통 타입(`src/game/types/game.ts`)은 시스템 담당이 관리하며 임의로 변경하지 않는다.

## DEC-008 — 시작 화면은 Figma 디자인을 React 레이어로 구현한다

- 날짜: 2026-08-06
- 상태: ACCEPTED
- 관련 질문: OQ-024, OQ-026

### 결정

시작 화면(Figma `Frame 1`, node `1:33`)을 Phaser 씬이 아니라 React 컴포넌트
`src/components/ui/TitleScreen.tsx`로 그린다. `ReadyScene`은 화면을 그리지 않고
`ui:continue` 이벤트만 기다린다. 시작 입력(키·클릭)도 React가 단독으로 받는다.

에셋은 `public/assets/title/`에 두고 `assetPath()`로 참조한다.
배치는 1920×1080 디자인 좌표를 그대로 쓰고, `--u`(디자인 1px의 실제 px) 하나로 스케일한다.

### 이유

- 배경 블러·웹폰트·투명 PNG 겹치기는 DOM이 Phaser보다 훨씬 짧게 끝난다.
- DEC-006에서 이미 "UI는 React DOM 오버레이"로 경계를 그었다. 시작 화면은 UI다.
- 입력 지점을 한 곳으로 모아야 런이 두 번 시작되지 않는다.

### 대안

- Phaser `ReadyScene`에서 이미지로 렌더 — 블러와 한글 웹폰트 처리 비용이 크고,
  캔버스 내부 좌표계에 묶여 1920×1080 디자인 좌표를 그대로 못 쓴다.
- Next.js `next/image` 정적 임포트 — `basePath` 처리는 편하지만 기존 `assetPath()`
  규약과 이중이 되고, `next-env.d.ts`가 없으면 `npm run typecheck`가 깨진다.

### 영향

- `src/components/ui/TitleScreen.tsx` 신규, `HUDOverlay`가 `phase === "READY"`에 렌더한다.
- `ReadyScene`에서 플레이스홀더 텍스트와 자체 입력 처리를 제거했다. 조작 안내가 사라져 OQ-026을 등록했다.
- `RunState.reset()`이 `phase` 필드를 직접 대입해 `phase:change`를 발행하지 않던 문제를 함께 고쳤다.
  이 이벤트가 없으면 React가 READY 화면을 띄우지 못한다.
- `theme.font.ui`(Pretendard)와 `app/globals.css`의 웹폰트 `@import`가 추가됐다.

## DEC-009 — 화면 연출은 GSAP, 전환은 ScreenFade 한 곳에서

- 날짜: 2026-08-06
- 상태: ACCEPTED
- 관련 질문: OQ-027

### 결정

- 시작 화면 등장과 로딩 화면 연출은 GSAP 타임라인으로 만든다. 이미 의존성에 있고 순서 제어가 쉽다.
- 화면 사이 전환은 `src/components/ui/ScreenFade.tsx` 하나만 쓴다.
  검게 덮은 시점(`onCovered`)에 다음 화면으로 넘기고 다시 걷는다.
- 시작 화면 → 전투 전환은 `none → cover → load → none` 3단계다.
  덮인 뒤 로딩 화면을 한 번 더 보여 주고 전투로 들어간다.
  그래서 `theme.z.loading`(60)이 `theme.z.transition`(50)보다 위다.
- 로딩 화면은 시작 화면 에셋 네 장을 미리 받고, **걷히기 시작할 때** 다음 화면을 먼저 붙인다.
  다 걷힌 뒤에 붙이면 그 사이 빈 화면이 보인다.
- 시작 화면 배경은 16:9 무대 밖에 두고 화면 전체를 덮는다(`object-fit: cover`).
  무대 안에 두면 16:9가 아닌 창에서 빈 띠가 남는다. 배경은 잘려도 되고 타이틀은 잘리면 안 된다.
- 모든 연출은 `gsap.matchMedia()`로 `prefers-reduced-motion`을 존중한다.

### 이유

- 전환 길이가 화면마다 달라지면 게임 전체의 리듬이 흐트러진다. 한 컴포넌트로 묶어 고정한다.
- 배경 이미지가 1MB를 넘어 프리로드 없이는 시작 화면에서 배경이 뒤늦게 튀어나온다.

### 대안

- CSS `@keyframes` — 요소별 순서를 맞추기 어렵고, 길이를 조정할 때 손댈 곳이 흩어진다.
- 전환 없이 즉시 교체 — 구현은 가장 짧지만 화면이 툭툭 끊긴다.
- 배경까지 `contain` — Figma 구도는 정확히 보존되지만 창 비율이 다르면 빈 띠가 남는다.

### 영향

- `LoadingScreen.tsx`, `ScreenFade.tsx`, `titleAssets.ts` 신규. `TitleScreen.tsx`에 등장 타임라인 추가.
- `HUDOverlay`가 로딩·전환 상태를 함께 관리한다.
- `theme.z`에 `loading: 40`, `transition: 50` 추가.
- `ornament.png`는 Figma 렌더 방향(상하 반전)으로 파일 자체를 뒤집었다.
  CSS `transform`으로 뒤집으면 GSAP이 같은 속성을 덮어써 충돌한다.
- 로딩 화면 디자인은 Figma 시안이 없어 임시안이다. OQ-027로 남겼다.

## DEC-010 — 시작 화면 메뉴와 소리 진입 방식

- 날짜: 2026-08-06
- 상태: ACCEPTED
- 관련 질문: OQ-027, OQ-028

### 결정

- 시작 화면은 "아무 키" 대신 **처음부터 / 이어하기 / 설정** 메뉴로 진입한다.
  서체는 Pretendard Light 흰색, 항목 배경은 가운데만 진한 가로 그라데이션이다.
- **이어하기는 비활성**이다. 세이브·로드는 MVP 범위 밖이라 UI만 두고 기능은 넣지 않는다. (OQ-028)
- 설정 화면은 **왼쪽 세로 아이콘 레일 + 오른쪽 행 목록** 구성이다(사운드 / 조작).
  소리는 마스터·배경음악·효과음 세 값을 둔다. 마스터는 나머지에 곱해서 쓴다.
  효과음은 아직 메뉴 소리에만 걸리므로 화면에 그 범위를 적는다.
  값은 `localStorage` 키 `null:audio` 하나에 JSON으로 저장한다.
- 배경음악은 로딩 화면에서 시작해 전투 전환과 함께 끈다. 메인 화면 전용이다.
- **첫 방문에는 안내 팝업을 먼저 띄운다.** 브라우저가 사용자 입력 전 소리를 막으므로
  이 버튼 클릭이 소리를 여는 입력 역할을 한다. 방문 여부만 `localStorage`에 남긴다.
- 마우스 커서는 mobicom 프로젝트 구현을 가져와 색만 바꿔 쓴다.
- 브라우저 기본 포커스 링은 지우지 않고 색만 붉은 톤으로 바꾼다.

### 이유

- 메뉴가 있어야 설정 진입점이 생기고, 심사자가 조작 방법을 짐작하지 않아도 된다.
- 자동 재생 차단은 우회할 수 없다. 안내 팝업이 규칙(CLAUDE.md 배포 규칙)과 요구를 동시에 만족시킨다.
- 포커스 링을 없애면 키보드 사용자가 위치를 잃는다. 색만 바꾸면 톤과 접근성을 모두 지킨다.

### 대안

- 자동 재생 시도 후 실패하면 무음 — 첫 방문자는 소리를 못 듣는다.
- 이어하기를 메뉴에서 제거 — 나중에 넣을 때 메뉴 배치를 다시 잡아야 한다.

### 영향

- `TitleBgm.tsx`, `SettingsPanel.tsx`, `FirstVisitPrompt.tsx`, `CursorFollower.tsx` 신규.
- `TitleScreen`이 메뉴와 설정 상태를 갖고, `HUDOverlay`가 볼륨·첫 방문 상태를 관리한다.
- `localStorage` 키 두 개를 쓴다: `null:visited`, `null:bgmVolume`.
- `theme.z`에 `prompt: 70`, `cursor: 9999` 추가.

## DEC-011 — 디렉터를 「기록자」로 재해석하고 전투 계약을 분리한다

- 날짜: 2026-08-06
- 상태: ACCEPTED
- 관련 질문: OQ-021 (RESOLVED), OQ-024

### 결정

**톤.** 기획서의 "AI 디렉터"(실험·분석하는 SF 존재)를 지금 만든 다크 판타지 화면에 맞춰
**기록하고 판결하는 존재**로 재해석한다. NULL은 돌아오지 못한 자들의 시험장이다.
- 화면 표기는 「기록」/「판결」 계열 한국어. `DIRECTOR ANALYSIS` 같은 영문 헤더는 쓰지 않는다.
- 영문은 `NOTICE`·`SETTINGS` 같은 소제목에만 남긴다.
- **코드 식별자(`DirectorPolicy`, `DirectorAnalysis` 등)는 바꾸지 않는다.** 표시 문구만 교체한다.

**전투 계약.** 플레이어·적·보스를 나눠서 만들 수 있도록 `src/game/types/combat.ts`에
충돌 그룹(`CombatArena`)과 데이터 규약을 정의한다.
- 엔티티는 서로를 직접 참조하지 않는다. 각자 자기 그룹에만 오브젝트를 넣는다.
- 누가 누구를 때렸는지는 **씬 한 곳에서만** 판정한다.
- 플레이어 위치는 `getPlayerPosition()`으로만 얻는다.
- 도형 팔레트는 `SILHOUETTE`/`TEXTURE` 한 곳에 모은다. 스프라이트가 오면 키만 교체한다. (OQ-024)

### 이유

- 시스템(분석 → 카운터 → 역기만 → 보스 가중치)은 그대로 두고 표현만 바꾸면 리팩터 비용이 0이다.
  식별자까지 바꾸면 검증해 둔 분류 규칙을 다시 확인해야 한다.
- 계약이 없으면 여러 담당이 같은 씬 파일을 동시에 고쳐 충돌한다. 실제로 이 계약 덕분에
  플레이어·적·보스·톤을 네 갈래로 나눠 병렬 작업할 수 있었다.

### 대안

- SF 톤 유지 — 이미 만든 아트(붉은 달·폐허)와 어긋나 아트를 다시 잡아야 한다.
- 엔티티가 서로를 직접 참조 — 구현은 빠르지만 파일 소유권을 나눌 수 없다.

### 영향

- `data/directorRules.ts`의 대사, `AnalysisPanel`·`DeceptionPanel`·`ResultPanel` 문구, `MVP_PLAN.md` 서술.
  임계값·가중치 숫자는 하나도 바뀌지 않았다.
- `types/combat.ts` 신규. `CombatScene`·`BossScene`이 충돌을 배선한다.
- 전투 수치는 아직 각 엔티티 파일 상단에 임시로 모여 있다. 밸런스 확정 후 `gameBalance.ts`로 옮긴다. (OQ-007)

## DEC-012 — 강화를 8종으로 늘리고 둘은 무기 자체를 바꾼다

- 날짜: 2026-08-07
- 상태: 확정

### 결정

강화를 6종에서 **8종**으로 늘린다. 추가한 둘은 무기 자체를 교체하는 강화다.

- `BLADE_REFORGED` (다시 벼린 검) — 피해 1.35배, 사거리 +14, 궤적이 붉은색에서 흰빛으로
- `BARREL_REFORGED` (개조된 총열) — 피해 1.4배, 탄속 1.25배, 탄 꼬리가 84 → 124로 길고 두껍게

### 근거

기존 6종은 전부 숫자만 바뀐다. 「예리한 날」을 골라도 화면에서는 아무것도 달라지지 않아
무엇을 얻었는지 플레이어가 알 수 없었다. 강화를 고르는 순간이 런의 리듬을 만드는 지점인데
그 보람이 보이지 않는 것은 손해다.

그래서 이 둘은 **수치와 이펙트를 같이 바꾼다.** 벼린 검은 궤적 색이 바뀌고 획이 굵어지며,
개조된 총열은 탄 꼬리가 눈에 띄게 길어진다. 다음 방에 들어서는 순간 손에 든 것이
달라졌음을 한 번의 공격으로 알 수 있다.

### 검토한 대안

- **6종 유지, 이펙트만 기존 강화에 붙이기** — 「예리한 날」이 색까지 바꾸면
  이름과 효과가 어긋난다. 날을 갈았는데 빛이 바뀔 이유가 없다.
- **무기 교체를 별도 시스템으로** — 인벤토리·장착 UI가 따라온다. MVP 범위 밖이다. (CLAUDE.md 규칙 3)

### 영향 범위

- `types/game.ts` — `UpgradeId`에 두 값 추가. 기존 값은 그대로라 다른 코드는 영향 없다.
- `data/upgrades.ts` — 정의 2개 추가. `UPGRADE_IDS`가 자동으로 8개가 되어 선택지에 등장한다.
- `systems/CombatVfx.ts` — `slashArc`·`createBulletTrail`에 기본값 있는 선택 인자 추가.
- `entities/Player.ts` — 수치 적용과 VFX 전달.
- `MVP_PLAN.md` — 강화 6종 → 8종으로 갱신.

적 체력과 공격력은 건드리지 않았다. 소프트 카운터 원칙은 그대로다. (DEC-004)

강화 지급 횟수는 여전히 2회다(OQ-016 미결정). 후보가 6종에서 8종으로 늘어난 만큼
특정 강화를 만날 확률은 낮아진다. 지급 횟수를 늘릴지는 플레이 테스트 후 결정한다.
