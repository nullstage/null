# AI 사용 기록 — 2026-08-08

## AI-002 — 적 패턴·강화 카드·Director 방 분류 구현 상태 조사

### 목적

팀원이 진행해 둔 전투 구현을 이어받기 전에, `docs/Plan.md`에 DONE으로 표시된
DirectorPolicy·적 3종·강화 시스템이 실제 코드에서 어디까지 동작하는지 확인하기 위해서다.
문서 표기만으로는 미결정 정책(OpenQuestions)과 실제 구현 여부가 뒤섞여 있어 구분이 필요했다.

### 사용 도구

Claude Code (Sonnet 5), 조사 전용 서브에이전트(Explore) 1개

### 대표 프롬프트

```text
팀원이 작업을 좀 해놨는데, 적 패턴 제작이랑 방 깼을 때 나오는 강화 카드를 더 구체화하고
싶다. 방을 깨면 근거리/원거리 패턴을 분석해서 다음 방을 바꾸는 것도 얼마나 구현돼있는지
확인해야 한다.
```

### AI 제안 요약

- 적 3종(ChaserEnemy·RangedEnemy·MobilityCounterEnemy)은 스탯이 아니라 상태머신 기반
  행동으로 차별화되어 있으며 완전히 구현됨을 파일:라인 근거와 함께 확인.
- 강화 8종이 전부 정의되고 `Player.ts`에서 실제 스탯에 적용됨을 확인. 다만 지급 횟수가
  2회로 고정돼 있고 OQ-016(3회 권장)이 코드에 반영되지 않았음을 지적.
- DirectorPolicy의 스타일 분류가 방 3(카운터 방)과 보스 패턴 가중치에는 실제로
  연결되지만, 방 2는 방 1 분석을 반영하지 않는 고정 프리셋임(OQ-010 미반영)을 지적.

### 최종 반영

조사 결과를 바탕으로 사용자에게 OQ-010(방2 반영 여부)과 OQ-016(강화 지급 횟수)을
확정하도록 질문했다. 결정된 내용(약한 카운터 적용 / 3회 지급)을 `DecisionLog.md`
DEC-013·DEC-014로 기록하고, DEC-013(강화 3회)은 바로 구현·검증까지 마쳤다.
DEC-014(방2 반영)는 구체적 반영 방식(스폰 순서 조정 / 적 1종 교체 / 축소판 카운터방)을
다시 질문해 결정을 받은 뒤 구현했다(AI-003).

### 사람의 수정 및 판단

- 방2 반영 방식은 AI가 임의로 확정하지 않았다. 방2가 방3 분석에서 "이전 방" 자리를
  차지해 35% 가중치를 그대로 받는 구조라(MVP_PLAN §4), 반영 방식에 따라 "방1 분석 →
  방2 구성 → 방3 분석"이 서로 되먹임하는 위험이 있다고 판단해 별도 결정 사항으로 분리했다.
- 강화 3회 지급은 결정되자마자 구현까지 진행했지만, 완료 보고 전에 반드시 실제
  브라우저 흐름을 관통시켜 검증하라는 프로젝트 규칙에 따라 빌드 성공만으로 끝내지 않고
  Playwright 헤드리스로 방1→방2→방3→강화(3회)→보스 진입까지 실제 클릭으로 재현했다.

## AI-003 — 방 2 소프트 카운터 구체안 구현

### 목적

DEC-014에서 방향("방 2도 방 1 분석을 약하게 반영")만 정해졌던 것을, 실제로 어떤
방식으로 반영할지 사용자에게 구체적 대안을 제시해 고르게 하고 구현하기 위해서다.

### 사용 도구

Claude Code (Sonnet 5)

### 대표 프롬프트

AskUserQuestion으로 제시한 세 대안(직접 대화 프롬프트 없음):

```text
1. 스폰 순서·타이밍만 조정 (적 종류·수 그대로)
2. 적 1종만 성향에 맞게 교체
3. 축소판 카운터 방 (counter_* 재사용, 2기로 축소)
```

각 대안에 방 1이 RANGED로 감지됐을 때 방 2 스폰 구성이 구체적으로 어떻게 되는지
미리보기로 붙여, "약하게 반영한다"는 말이 실제로 어떤 방 모양이 되는지 보고 고르게 했다.

### AI 제안 요약

세 대안 모두 구현 가능하다고 판단했지만, 축소판(3안)이 방 3 텔레메트리 되먹임
위험이 가장 크다는 점을 미리 경고했다 — 방 2를 특정 스타일로 완전히 밀어붙이면
방 1의 분석 결과가 방 2 자신의 데이터를 통해 방 3 분석에 다시 강화되는 자기실현적
구조가 될 수 있어서다.

### 최종 반영

사용자가 3안(축소판)을 선택했다. 방 3용 카운터 조합에서 다수 그룹(2기)만 남기고
소수 그룹(1기)은 빼는 방식으로 `room_2_soft_ranged`·`room_2_soft_melee`·
`room_2_soft_mobile` 3개 프리셋을 추가하고, `CombatScene.resolveRoomId`가 방 1
단독 분류 결과로 방 2 프리셋을 고르도록 구현했다. `MVP_PLAN.md` §5에 규칙을
문서화하고 `DecisionLog.md` DEC-014를 `ACCEPTED`로 갱신했다.

### 사람의 수정 및 판단

- 위험을 알고도 축소판을 선택한 것은 사용자 판단이다. AI는 대안과 위험만 제시하고
  결정은 임의로 하지 않았다(CLAUDE.md "핵심 전투 방식/게임 루프 변경은 질문" 원칙).
- 완료 보고 전 실제 브라우저 검증 규칙에 따라, 빌드·타입체크만으로 끝내지 않고
  Playwright로 실제 원거리 전투(모드 전환·사격)를 재현해 방 1이 RANGED로 분류되고
  방 2가 실제로 축소판(2기)으로 바뀌는 것을 스크린샷까지 남겨 확인했다.
- 헤드리스 자동화 중 `page.keyboard.press()`가 Phaser의 `JustDown` 판정을 놓쳐
  입력이 무시되는 문제를 만났다 — 제품 버그가 아니라 테스트 방식 문제임을 먼저
  확인(이동 키는 정상 동작)한 뒤 `down`→대기→`up` 방식으로 바꿔 해결했다.
